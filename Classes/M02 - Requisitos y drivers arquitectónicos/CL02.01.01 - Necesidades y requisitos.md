# CL02.01.01 — Necesidades y requisitos

## Ficha de la clase

- **Módulo:** M02 — Requisitos y drivers arquitectónicos
- **Competencia principal:** C03 — identificar y priorizar los drivers arquitectónicos relevantes.
- **Nivel esperado:** IDENTIFICAR.
- **Duración sugerida:** 60–90 minutos.
- **Prerrequisitos:** CL01.01.01 — Concepto y propósito de la arquitectura; vocabulario básico de elementos, relaciones y atributos de calidad.
- **Pregunta guía:** ¿Qué necesita realmente el sistema y qué requisitos deberían influir en su arquitectura?
- **Evidencia de aprendizaje:** lista breve de necesidades y requisitos clasificados, con al menos un requisito funcional, uno de calidad y una restricción.

## 1. Objetivos de aprendizaje

Al terminar, podrás:

1. Distinguir una necesidad del usuario de un requisito del sistema.
2. Separar requisitos funcionales, requisitos de calidad y restricciones.
3. Identificar requisitos vagos que necesitan aclaración.
4. Convertir una necesidad general en una afirmación que pueda verificarse.
5. Explicar por qué no todos los requisitos tienen la misma importancia arquitectónica.

## 2. Idea central

La arquitectura no debe empezar eligiendo una tecnología. Primero hay que entender qué problema se intenta resolver, quién necesita el sistema y qué condiciones debe cumplir. Los requisitos aportan evidencia para tomar decisiones arquitectónicas; no son una excusa para diseñar de más.

Una necesidad expresa un resultado que alguien requiere. Un requisito precisa qué debe hacer el sistema o bajo qué condiciones debe operar. Una necesidad como «la tienda debe ser rápida» todavía es demasiado vaga para evaluar una solución.

## 3. Tres categorías útiles

### 3.1 Requisitos funcionales

Describen capacidades o comportamientos que el sistema debe ofrecer.

Ejemplos para una tienda en línea:
- El cliente puede consultar el catálogo.
- El cliente puede confirmar una compra.
- El sistema registra el estado de cada pedido.

### 3.2 Requisitos de calidad

Describen propiedades relevantes del comportamiento del sistema, como rendimiento, disponibilidad, seguridad, modificabilidad o facilidad de operación. Para que sean útiles, deben expresarse en un contexto verificable.

Vago: «El catálogo debe ser rápido».

Más verificable: «Durante una carga de 500 usuarios concurrentes, el 95 % de las consultas del catálogo debe responder en menos de 2 segundos».

La cifra es un ejemplo para practicar, no una recomendación universal. Los objetivos reales deben acordarse con las personas interesadas y validarse con datos.

### 3.3 Restricciones

Son condiciones que limitan las soluciones posibles, por ejemplo:
- Debe integrarse con el proveedor de pagos contratado.
- El despliegue debe ejecutarse en la infraestructura aprobada por la organización.
- El equipo debe utilizar una tecnología por una obligación contractual.

Una preferencia tecnológica no es automáticamente una restricción. Conviene preguntar si es obligatoria, negociable o simplemente familiar para el equipo.

## 4. De la necesidad al requisito verificable

Usa este proceso breve:

1. **Identificar al interesado:** ¿quién tiene la necesidad?
2. **Precisar el contexto:** ¿en qué situación ocurre?
3. **Describir el resultado esperado:** ¿qué debe suceder?
4. **Definir una medida o condición observable:** ¿cómo sabremos si se cumple?
5. **Confirmar la prioridad:** ¿qué consecuencia tendría no cumplirlo?

Ejemplo:

- Necesidad: los clientes abandonan compras cuando hay mucho tráfico.
- Pregunta de aclaración: ¿la demora ocurre al consultar el catálogo, reservar inventario o confirmar el pago?
- Requisito provisional: durante el periodo de mayor demanda, el 95 % de las consultas de catálogo debe responder en menos de 2 segundos.
- Validación pendiente: confirmar la carga esperada, la métrica, el entorno de prueba y el objetivo aceptable con el negocio.

No atribuyas toda lentitud a la arquitectura antes de medir dónde se produce.

## 5. ¿Cuáles requisitos importan para la arquitectura?

No todo requisito obliga a tomar una decisión arquitectónica significativa. Un requisito es especialmente relevante cuando puede cambiar la estructura del sistema, sus límites, sus interacciones, sus tecnologías o sus estrategias operativas.

Preguntas útiles:
- ¿Afecta a varios componentes o a una frontera entre ellos?
- ¿Impone un objetivo de calidad difícil de cumplir?
- ¿Introduce una integración externa o una restricción obligatoria?
- ¿Qué pasa si no se cumple?
- ¿Podemos verificarlo con una prueba o medición?

Una decisión arquitectónica suele implicar compromisos. Por ejemplo, separar un componente podría permitir despliegues independientes, pero añadir comunicación de red y trabajo operativo. No se debe elegir esa solución sin conocer la necesidad que la justifica.

## 6. Caso guiado: una tienda en línea

La tienda permite consultar productos y registrar pedidos. En campañas promocionales, algunos usuarios reportan lentitud. El negocio solicita «hacerla escalable». No se han tomado mediciones ni se ha precisado qué operación es lenta.

Clasificación inicial:

| Enunciado | Clasificación | ¿Está suficientemente definido? |
|---|---|---|
| El cliente puede consultar productos. | Funcional | Parcialmente; faltan reglas del catálogo. |
| El 95 % de las consultas debe responder en menos de 2 segundos bajo una carga acordada. | Calidad | Es medible, pero hay que acordar carga, entorno y objetivo. |
| Debe utilizarse el proveedor de pagos contratado. | Restricción o requisito de integración | Confirmar si es obligatorio y documentar su interfaz. |
| La aplicación debe ser escalable. | Objetivo vago de calidad | No; hay que precisar carga, operación afectada y criterio de éxito. |

El siguiente paso no es migrar a microservicios. Es investigar el síntoma, acordar medidas y obtener evidencia para decidir qué alternativa merece probarse.

## 7. Actividad individual

Clasifica estos enunciados como funcionales, de calidad, restricciones o necesidades todavía vagas:

A. «El cliente puede cancelar un pedido antes de que sea enviado».  
B. «El sistema debe ser seguro».  
C. «La empresa exige desplegar en su plataforma aprobada».  
D. «Durante la campaña, el 99,9 % de las solicitudes de consulta debe completarse correctamente en el periodo acordado».  
E. «Los usuarios dicen que comprar es complicado».

Para B y E, escribe una pregunta que permita aclararlos. Para D, indica qué contexto o definición falta antes de poder verificarlo.

## 8. Comprobación de comprensión

Responde sin consultar el texto:

1. ¿Cuál es la diferencia entre una necesidad y un requisito verificable?
2. ¿Por qué «la aplicación debe ser rápida» no basta para evaluar una decisión?
3. ¿Qué diferencia hay entre un requisito de calidad y una restricción?
4. Si una aplicación es lenta, ¿por qué no se debe decidir inmediatamente migrar a microservicios?

### Criterios de revisión

La evidencia es suficiente para esta clase si el estudiante:
- clasifica correctamente los ejemplos;
- identifica al menos dos requisitos vagos;
- propone preguntas concretas para aclararlos;
- explica que las decisiones arquitectónicas deben justificarse con necesidades y evidencia, no con tendencias tecnológicas.

## 9. Errores frecuentes

- **Confundir una solución con un requisito:** «usar una cola» describe una alternativa técnica, no el resultado que necesita el negocio.
- **Usar adjetivos sin medida:** «rápido», «seguro» y «escalable» requieren contexto y criterios observables.
- **Tratar todas las peticiones como obligatorias:** confirmar prioridad, alcance y autoridad de quien solicita.
- **Suponer que un requisito implica una arquitectura concreta:** normalmente existen varias alternativas con distintos compromisos.
- **Inventar métricas:** las cifras didácticas deben validarse con los interesados y con mediciones del sistema.
