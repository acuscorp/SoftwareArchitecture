### 4. Fundamentos y elementos de las decisiones arquitectónicas

#### 4.1. Arquitectura y decisiones

Bass, Clements y Kazman definen la arquitectura mediante las estructuras necesarias para razonar sobre un sistema: elementos de software, relaciones entre ellos y propiedades de ambos. En el capítulo 2 explican por qué la arquitectura importa, entre otras razones porque conserva decisiones de diseño tempranas y establece restricciones para la implementación.

Por tanto, una decisión es arquitectónicamente relevante cuando determina o condiciona aspectos que forman parte de esas estructuras, sus relaciones o propiedades. No basta con que la decisión sea difícil, costosa o tomada al principio del proyecto.

Ejemplos de decisiones que determinan aspectos arquitectónicos:

- asignar a un elemento la responsabilidad exclusiva de modificar el estado de una orden;
- establecer qué elementos deben comunicarse y mediante qué mecanismo;
- definir cómo se representan y organizan los datos compartidos;
- establecer cómo se arbitra el acceso a un recurso compartido;
- asignar módulos a procesos o unidades de despliegue;
- permitir que una implementación se seleccione al iniciar el sistema;
- seleccionar una tecnología que condiciona cómo se materializan otras decisiones.

Una formulación precisa identifica la elección y el aspecto que queda determinado.

**Formulación imprecisa:** «El sistema será moderno y escalable».

**Formulación identificable:** «El módulo de pedidos será el único elemento autorizado para cambiar el estado de una orden; los demás módulos solicitarán el cambio mediante su interfaz».

La segunda formulación permite identificar un elemento, una responsabilidad y una relación con otros elementos.

#### 4.2. Decisión arquitectónica y detalle local

No toda decisión de diseño o implementación determina la arquitectura. La distinción depende de qué queda condicionado y de si la decisión modifica una estructura, una relación o una propiedad relevante del sistema.

| Ejemplo | Alcance descrito | Explicación |
|---|---|---|
| Cambiar el nombre de una variable privada dentro de un módulo | Local | No modifica la responsabilidad del módulo ni sus relaciones externas. |
| Elegir entre dos algoritmos internos que mantienen el mismo contrato y las mismas propiedades externas especificadas | Local en el caso descrito | La elección permanece dentro del elemento y no altera sus relaciones. |
| Establecer qué módulo es autoridad sobre el estado de una orden | Arquitectónico | Determina responsabilidades y condiciona la interacción de otros módulos. |
| Establecer que dos componentes se comunican mediante una cola de mensajes | Arquitectónico | Determina un mecanismo de coordinación entre elementos. |
| Elegir una biblioteca interna que no altera contratos, dependencias ni restricciones externas | Local en el caso descrito | La tecnología queda encapsulada en un elemento. |
| Elegir una plataforma que obliga a todos los módulos a usar un protocolo y un modelo de ejecución específicos | Arquitectónico en el caso descrito | La selección condiciona varias partes y sus relaciones. |

La etiqueta no se asigna por el nombre de la tecnología, el tamaño del cambio o el cargo de quien toma la decisión. Se explica a partir de los efectos descritos.

#### 4.3. No confundir decisiones con categorías de cambio

*Software Architecture in Practice* (3.ª ed.), §2.2, distingue tres categorías de cambio:

- **Cambio local:** puede realizarse modificando un único elemento.
- **Cambio no local:** requiere modificar varios elementos, pero mantiene el enfoque arquitectónico existente.
- **Cambio arquitectónico:** afecta las formas fundamentales en que los elementos interactúan y probablemente requiere cambios en distintas partes del sistema.

Estas categorías describen el alcance de un **cambio**, no constituyen una taxonomía de las siete categorías de decisiones del capítulo 4.

Ejemplo completo:

- Cambiar una regla interna del módulo de precios, sin modificar su interfaz: cambio local.
- Añadir un campo a la base de datos, modificar el módulo de precios y exponer el resultado en la interfaz, manteniendo la estructura general: cambio no local.
- Sustituir la interacción cliente-servidor por una interacción entre pares: cambio arquitectónico.

No se debe inferir que toda decisión que afecta varios archivos es arquitectónica. Se debe identificar qué cambia en las estructuras y relaciones del sistema.

#### 4.4. La arquitectura restringe la implementación

El capítulo 2, §2.6, explica que la arquitectura establece restricciones para la implementación posterior. Una vez que una estructura o relación se ha establecido, la implementación debe respetarla.

Ejemplo:

1. La decisión establece que el módulo de pedidos es responsable de cambiar el estado de una orden.
2. Los demás módulos deben solicitar ese cambio mediante la interfaz del módulo de pedidos.
3. Una implementación en la que el módulo de inventario modifica directamente la tabla de estados contradice la responsabilidad establecida.

La arquitectura no determina cada línea de código. Delimita decisiones posteriores y deja espacio para detalles de implementación que respeten sus restricciones.

#### 4.5. Decisiones tempranas y evolución

El capítulo 2, §2.5, explica que la arquitectura conserva decisiones de diseño tempranas que pueden ser fundamentales y difíciles de cambiar. Esto no significa que todas las decisiones arquitectónicas se tomen al inicio ni que todas sean irreversibles.

Una decisión puede condicionar otras porque establece una responsabilidad, una relación o un contrato que otros elementos utilizan. Si cambia, es necesario identificar qué elementos dependen de ella.

**Ejemplo:** si tres módulos utilizan la interfaz de un módulo de pedidos para cambiar estados, modificar esa interfaz puede exigir cambios en los tres consumidores. El dato relevante es la dependencia explícita; no se debe afirmar que todo el sistema tendrá que reescribirse.

#### 4.6. Elementos para describir una decisión arquitectónica

Para describir una decisión sin agregar información que el caso no proporciona, identifica los siguientes elementos cuando estén disponibles:

- **Situación o problema:** circunstancia que hace necesario tomar o registrar la decisión. Incluye únicamente la información expresamente proporcionada.
- **Contexto:** hechos, condiciones y restricciones existentes en el momento de la decisión.
- **Elección:** qué se decidió, expresado de forma concreta.
- **Elementos afectados:** módulos, componentes, conectores, procesos u otros elementos mencionados.
- **Aspecto arquitectónico determinado:** responsabilidad, interacción, representación de datos, recurso, correspondencia, momento de vinculación o tecnología.
- **Justificación documentada:** razones que la fuente o el ADR atribuye explícitamente a la decisión. Si no aparecen, se registra como «No especificada».
- **Consecuencias conocidas:** efectos que el escenario o el registro describen explícitamente, sin deducir efectos adicionales.
- **Restricciones y dependencias:** condiciones que la decisión impone o relaciones que quedan establecidas con otras decisiones o elementos.
- **Información no especificada:** razones, consecuencias, requisitos o condiciones ausentes de la fuente y que, por tanto, no deben suponerse.

Estos elementos sirven para explicar una decisión ya descrita. La categoría identifica qué aspecto arquitectónico determina; el tiempo de vinculación indica cuándo y mediante qué mecanismo se fija una variación, si esos datos están disponibles.

En esta clase se puede identificar y explicar una justificación que ya esté documentada. No se pide construir una justificación propia mediante generación y comparación de alternativas, análisis de trade-offs o selección de una solución. Esos desempeños corresponden a M02.

### 5. Las siete categorías de decisiones arquitectónicas

*Software Architecture in Practice* (3.ª ed.), capítulo 4, §4.6, presenta siete categorías. Los autores aclaran que las categorías pueden solaparse y que una decisión puede pertenecer a más de una. Su propósito es dividir racionalmente las preocupaciones para comprobar que los aspectos importantes hayan sido considerados.

#### 5.1. Asignación de responsabilidades (*Allocation of responsibilities*)

Esta categoría comprende decisiones sobre:

1. identificar responsabilidades importantes, incluidas funciones del sistema, infraestructura arquitectónica y satisfacción de atributos de calidad;
2. asignar esas responsabilidades a elementos de desarrollo y de ejecución, como módulos, componentes y conectores.

Preguntas para reconocerla:

- ¿Qué responsabilidad debe existir?
- ¿A qué elemento se asigna?
- ¿Qué elemento es responsable de ejecutar o mantener esa responsabilidad?

**Ejemplo:** el módulo de pedidos valida las transiciones permitidas de una orden y es el único que puede modificar su estado. Los módulos de interfaz e inventario no realizan esa modificación directamente.

La decisión no consiste en nombrar una clase. Consiste en asignar una responsabilidad a un elemento arquitectónico.

#### 5.2. Modelo de coordinación (*Coordination model*)

Los elementos del software interactúan mediante mecanismos diseñados. El conjunto de decisiones sobre esos mecanismos y sus propiedades constituye el modelo de coordinación.

Incluye decisiones sobre:

- qué elementos deben coordinarse y cuáles tienen prohibido coordinarse;
- propiedades de la coordinación, como oportunidad, actualidad, completitud, corrección y consistencia;
- mecanismos de comunicación entre elementos del sistema, sistemas externos y entidades externas;
- comunicación con estado o sin estado;
- comunicación síncrona o asíncrona;
- entrega garantizada o no garantizada;
- propiedades de rendimiento, como throughput y latencia.

**Ejemplo:** después de confirmar una orden, el módulo de pedidos publica un evento en una cola; el módulo de notificaciones consume ese evento posteriormente. La decisión establece una interacción asíncrona entre esos elementos.

No se debe concluir que la comunicación asíncrona es siempre mejor. Esta clase identifica qué determina el modelo de coordinación; no compara alternativas.

#### 5.3. Modelo de datos (*Data model*)

El modelo de datos es el conjunto de representaciones de datos relevantes para el sistema y la manera de interpretarlas.

Las decisiones de esta categoría incluyen:

- elegir abstracciones principales de datos, sus operaciones y propiedades;
- determinar cómo se crean, inicializan, consultan, persisten, manipulan, traducen y destruyen los datos;
- definir metadatos necesarios para interpretar los datos de forma consistente;
- organizar los datos, por ejemplo, en una base relacional, una colección de objetos o ambas;
- definir correspondencias cuando los datos se mantienen en representaciones o ubicaciones diferentes.

**Ejemplo:** el sistema representa una orden mediante un identificador, una lista de líneas, un importe y un estado. La información de pago se representa separadamente y mantiene una referencia al identificador de la orden.

La categoría no se reduce a seleccionar PostgreSQL, MongoDB u otro producto. La representación, organización e interpretación de los datos también forman parte del modelo.

#### 5.4. Gestión de recursos (*Management of resources*)

Un arquitecto puede necesitar arbitrar el uso de recursos compartidos. Los recursos pueden ser:

- **Físicos:** CPU, memoria, batería, buffers de hardware, reloj del sistema y puertos de entrada/salida.
- **Lógicos:** locks, buffers de software, pools de hilos y código no seguro para concurrencia.

Las decisiones incluyen:

1. identificar los recursos que deben gestionarse y establecer sus límites;
2. determinar qué elementos administran cada recurso;
3. determinar cómo se comparten y qué estrategia de arbitraje se usa ante contención;
4. determinar qué ocurre cuando un recurso se satura.

**Ejemplo:** el trabajador de notificaciones utiliza un pool de ocho hilos y la cola admite hasta mil mensajes pendientes. Cuando la cola alcanza su capacidad, el productor recibe un rechazo y registra la notificación como no encolada. Estos valores y comportamientos forman parte de la especificación del ejemplo, no son recomendaciones universales.

#### 5.5. Mapeo entre elementos arquitectónicos (*Mapping among architectural elements*)

La arquitectura necesita correspondencias entre elementos de distintas estructuras y entre elementos de software y elementos del entorno.

Ejemplos de mapeos descritos por Bass et al.:

- módulos con elementos de ejecución;
- elementos de ejecución con procesadores;
- elementos del modelo de datos con almacenes de datos;
- módulos y elementos de ejecución con unidades de entrega.

**Ejemplo:** el módulo de notificaciones se implementa en un proceso de trabajador separado; los módulos web, pedidos, pagos e inventario se ejecutan en el proceso de aplicación. Esta decisión establece una correspondencia entre módulos y procesos.

No basta con decir que dos componentes están conectados. Se debe identificar qué elementos se corresponden y de qué estructuras provienen.

#### 5.6. Decisiones de tiempo de vinculación (*Binding time decisions*)

Estas decisiones introducen rangos permitidos de variación. Una variación puede fijarse en distintos momentos del ciclo de vida y por diferentes participantes, desde el diseño por un desarrollador hasta la ejecución por un usuario.

Una decisión de tiempo de vinculación establece:

- el alcance de la variación;
- el momento del ciclo de vida en que se resuelve;
- el mecanismo utilizado para conseguir esa variación.

Las otras seis categorías también tienen una decisión de tiempo de vinculación asociada.

Ejemplos:

- seleccionar módulos durante la construcción mediante un archivo de construcción parametrizado;
- negociar protocolos durante la ejecución;
- reconocer un periférico conectado durante la ejecución y descargar su controlador;
- descargar la versión de una aplicación adecuada para el dispositivo del usuario.

Al considerar momentos de vinculación, Bass et al. indican que deben tenerse en cuenta tanto el coste de implementar el mecanismo como el coste de modificar una elección ya implementada. Esta clase presenta esa relación, pero no pide calcular ni comparar esos costes.

**Ejemplo:** el proveedor de pagos se selecciona al iniciar el proceso a partir de una variable de configuración. El proveedor permanece fijo durante la ejecución y solo cambia al reiniciar el proceso con otra configuración. El momento, alcance y mecanismo están expresamente definidos.

#### 5.7. Selección de tecnologías (*Choice of technology*)

Toda decisión arquitectónica debe materializarse finalmente mediante tecnologías específicas. La tecnología puede haber sido impuesta antes de comenzar el diseño arquitectónico; en ese caso, se convierte en una restricción para decisiones de las otras categorías. En otros casos, el arquitecto selecciona tecnologías para materializar las decisiones.

Esta categoría incluye decisiones sobre:

- qué tecnologías están disponibles para realizar las decisiones de las otras categorías;
- si las herramientas de desarrollo, simulación y pruebas son adecuadas;
- si existe familiaridad interna y soporte externo suficiente;
- qué efectos secundarios produce la tecnología, por ejemplo, mecanismos de coordinación obligatorios o límites para gestionar recursos;
- si la tecnología es compatible con la plataforma existente y puede comunicarse, monitorizarse y administrarse junto a ella.

**Ejemplo:** se selecciona RabbitMQ como tecnología para implementar la cola de mensajes del caso. RabbitMQ es la tecnología concreta; la decisión de que pedidos y notificaciones se coordinen de forma asíncrona pertenece al modelo de coordinación.

Una tecnología puede condicionar decisiones de otras categorías. Por ello, la selección tecnológica no debe explicarse de manera aislada.

#### 5.8. Resumen comparativo

| Categoría | Pregunta central | Qué determina |
|---|---|---|
| Asignación de responsabilidades | ¿Quién se hace responsable de qué? | Responsabilidades asignadas a elementos. |
| Modelo de coordinación | ¿Qué elementos interactúan y cómo? | Mecanismos y propiedades de interacción. |
| Modelo de datos | ¿Cómo se representan, organizan e interpretan los datos? | Abstracciones, operaciones, organización y persistencia. |
| Gestión de recursos | ¿Qué recursos se administran y cómo se arbitran? | Límites, propietarios y estrategias de uso compartido. |
| Mapeo entre elementos | ¿Qué elemento corresponde a qué unidad de ejecución, entrega o entorno? | Correspondencias entre estructuras. |
| Tiempo de vinculación | ¿Cuándo, dónde y mediante qué mecanismo se fija una variación? | Alcance, momento y mecanismo de variación. |
| Selección de tecnologías | ¿Con qué tecnologías se materializan las decisiones? | Tecnologías, herramientas, compatibilidad y soporte. |

**Importante:** una decisión puede involucrar más de una categoría. Se puede identificar una categoría principal para explicar el aspecto central y mencionar otras cuando los datos de la decisión lo justifiquen.

### 6. Dependencias entre decisiones

#### 6.1. Qué es una dependencia

Una decisión depende de otra cuando su formulación o implementación presupone una condición establecida por la otra. La relación debe poder explicarse con los datos del sistema; no basta con que las decisiones aparezcan juntas.

Ejemplo:

- Decisión A: el módulo de pedidos es el único que cambia el estado de una orden.
- Decisión B: los demás módulos solicitan cambios de estado mediante la interfaz de pedidos.

B depende de A porque la interfaz y el comportamiento de los consumidores respetan la responsabilidad asignada a pedidos.

#### 6.2. Restricciones posteriores

Una decisión puede limitar cómo se implementan elementos posteriores. Para explicarlo:

1. identifica la decisión que ya está establecida;
2. identifica el elemento o decisión posterior;
3. describe qué condición debe respetar;
4. señala qué parte de la implementación quedaría en contradicción si no la respeta.

No se requiere generar alternativas ni evaluar cuál produce mejores resultados.

#### 6.3. Relación con la evolución

Si cambia una decisión, se deben revisar los elementos que dependen de ella. El alcance del cambio depende de las relaciones existentes.

**Ejemplo con datos completos:** el módulo de pedidos publica el evento OrderConfirmed; el módulo de notificaciones lo consume; el módulo de inventario no consume ese evento. Si se modifica el nombre del evento, el consumidor registrado debe actualizar su contrato. Con la información proporcionada, se identifica al módulo de notificaciones como consumidor afectado. No se puede afirmar que inventario resulte afectado.

### 7. Razonamiento y documentación de decisiones

#### 7.1. Por qué documentar

Una decisión documentada permite que otras personas comprendan qué se estableció y en qué contexto. También facilita revisar las consecuencias cuando el sistema evoluciona o cuando nuevos integrantes necesitan entender por qué existe una restricción.

La documentación arquitectónica descrita por Bass et al. en el capítulo 18 sirve, entre otros propósitos, para comunicar, educar, analizar y orientar la construcción. En esta clase se presenta ADR como un formato breve de registro de decisiones, no como sustituto de la documentación arquitectónica completa.

#### 7.2. Elementos de un ADR

*Software Architecture: The Hard Parts*, de Richards, Ford, Sadalage y Dehghani, capítulo 1, presenta ADR como archivos de texto breves que registran una decisión específica. El formato que utiliza incluye:

- **Título:** frase nominal breve que identifica la decisión.
- **Contexto:** descripción breve del problema y las condiciones en las que se toma la decisión.
- **Decisión:** declaración de lo que se hará y la justificación que el autor del registro haya documentado.
- **Consecuencias:** efectos de aplicar la decisión que el registro identifica, incluidos los trade-offs que sus autores hayan considerado.

En esta clase, el estudiante identifica y explica esos cuatro campos cuando están presentes en el ADR. La justificación documentada forma parte del campo **Decisión** en el formato descrito por la fuente; no constituye un quinto campo obligatorio. Puede describir una justificación o un trade-off ya documentado, pero no debe inventarlos ni realizar una comparación propia de alternativas para completar el registro. Si la fuente no proporciona una razón o consecuencia, debe indicarse «No especificada» en lugar de deducirla.

El **estado** se muestra como metadato adicional en el ejemplo de esta clase, no como uno de los cuatro campos del formato aquí atribuido a *Software Architecture: The Hard Parts*. Si se utiliza, debe reflejar el proceso real del equipo; no se debe marcar una decisión como aceptada si no existe esa confirmación.

#### 7.3. ADR de ejemplo con información completa

El siguiente ADR es un ejemplo didáctico autocontenido. Todos los datos que contiene están definidos aquí; no representa una decisión real de una organización.

**ADR-001 — Autoridad sobre el estado de pedidos**

| Campo | Contenido |
|---|---|
| Estado (metadato adicional del ejemplo) | Aceptado |
| Contexto | El sistema tiene módulos web, pedidos, pagos, inventario y notificaciones. El estado de cada orden es consultado por web y notificaciones. Se requiere que exista un único elemento responsable de validar y registrar sus transiciones. |
| Decisión | El módulo de pedidos será el único elemento autorizado para validar y modificar el estado de una orden. Los demás módulos consultarán el estado mediante la interfaz de pedidos y solicitarán cualquier cambio a través de esa misma interfaz. La justificación documentada es concentrar en pedidos la responsabilidad de validar transiciones y mantener el estado, evitando que los otros módulos implementen reglas distintas para modificarlo. |
| Consecuencias | Los módulos web y notificaciones deben utilizar la interfaz de pedidos. Los cambios de estado quedan centralizados en pedidos. Si cambia la interfaz, deben revisarse sus consumidores. |

Este registro no presenta alternativas ni demuestra que la decisión sea la mejor posible. Su propósito es mostrar cómo comunicar una decisión y sus efectos conocidos.

#### 7.4. Límites de ADR

- Un ADR registra una decisión; no describe por sí solo toda la arquitectura.
- No sustituye diagramas, vistas, contratos ni documentación operativa.
- No demuestra que la decisión sea correcta.
- No reemplaza el proceso de generar y comparar alternativas.
- Su contenido debe distinguir hechos, razones y consecuencias conocidas de las hipótesis pendientes.

### 8. Caso guiado — Sistema de pedidos y pagos

**[EJEMPLO RESUELTO — Observa cómo se identifican las categorías]**

Este caso se utiliza también en la práctica guiada. La descripción es completa para las decisiones que se analizarán.

#### 8.1. Descripción del sistema

Una tienda en línea procesa pedidos. El sistema está compuesto por cinco módulos lógicos:

1. **Web:** recibe las solicitudes de los clientes y muestra la información de las órdenes.
2. **Pedidos:** valida y mantiene el estado de cada orden.
3. **Pagos:** envía solicitudes al proveedor externo de pagos y registra el identificador y resultado recibido.
4. **Inventario:** consulta existencias y reserva unidades para una orden confirmada.
5. **Notificaciones:** envía el correo de confirmación al cliente.

Los módulos tienen las siguientes reglas y relaciones:

- Solo Pedidos puede cambiar el estado de una orden.
- Web consulta el estado a Pedidos.
- Pagos informa a Pedidos el resultado de una operación de pago.
- Inventario recibe de Pedidos la orden confirmada y reserva las unidades solicitadas.
- Pedidos publica el evento OrderConfirmed en una cola.
- Notificaciones consume OrderConfirmed y envía el correo.
- El correo no se envía desde el proceso que atiende la solicitud web.

Los datos de una orden son: identificador, fecha, líneas de producto, importe total y estado. Los datos de pago son: identificador de pago, identificador de orden, importe y resultado. El inventario mantiene identificador de producto, cantidad disponible y cantidad reservada.

La configuración de ejecución es:

- Web, Pedidos, Pagos e Inventario se ejecutan dentro del proceso de aplicación.
- Notificaciones se ejecuta en un proceso de trabajador independiente.
- Ambos procesos se despliegan en máquinas virtuales Linux.
- El trabajador de notificaciones usa un pool de ocho hilos.
- La cola de notificaciones admite hasta mil mensajes pendientes. Al alcanzar ese límite, el productor recibe un rechazo y registra la notificación como no encolada.
- El proveedor de pagos se selecciona al iniciar el proceso mediante la variable PAYMENT_PROVIDER; el valor no cambia hasta reiniciar el proceso.
- Las tecnologías utilizadas son Java 21, PostgreSQL 16, RabbitMQ 3.13 y comunicación HTTP/JSON sobre TLS.

No hay otros elementos, protocolos, reglas o garantías definidos para este caso. No deben agregarse.

#### 8.2. Decisiones identificadas

| ID | Decisión expresamente descrita | Categoría principal | Aspecto determinado |
|---|---|---|---|
| D1 | Solo Pedidos valida y modifica el estado de una orden. | Asignación de responsabilidades | Autoridad sobre la transición de estado. |
| D2 | Pedidos publica OrderConfirmed y Notificaciones lo consume desde una cola. | Modelo de coordinación | Interacción asíncrona entre dos módulos. |
| D3 | Orden y pago utilizan las representaciones y campos descritos en el escenario. | Modelo de datos | Estructura y relación de los datos de orden y pago. |
| D4 | El trabajador usa ocho hilos y la cola admite mil mensajes; al llenarse, rechaza el mensaje y registra que no se encoló. | Gestión de recursos | Límite, uso y comportamiento ante saturación. |
| D5 | Notificaciones se ejecuta en un proceso separado; los otros cuatro módulos se ejecutan en el proceso de aplicación. | Mapeo entre elementos | Correspondencia de módulos con procesos. |
| D6 | El proveedor se selecciona al inicio con PAYMENT_PROVIDER y permanece fijo hasta reinicio. | Tiempo de vinculación | Momento, alcance y mecanismo de selección. |
| D7 | El sistema utiliza Java 21, PostgreSQL 16, RabbitMQ 3.13 y HTTP/JSON sobre TLS. | Selección de tecnologías | Tecnologías que materializan el sistema. |

#### 8.3. Una decisión puede relacionarse con otras categorías

D2 se clasifica principalmente como modelo de coordinación porque define cómo se comunican Pedidos y Notificaciones. También utiliza una tecnología concreta: RabbitMQ. La existencia de esa tecnología no cambia el aspecto principal de D2.

D5 es un mapeo porque asigna módulos lógicos a procesos de ejecución. No es una decisión de asignación de responsabilidades: las responsabilidades ya están descritas por D1 y por la descripción de los módulos.

D6 es una decisión de tiempo de vinculación porque especifica cuándo se selecciona el proveedor, quién o qué mecanismo lo selecciona y cuánto dura esa selección.

#### 8.4. Dependencia descrita

D2 establece que Notificaciones consume el evento que publica Pedidos. Por tanto, Notificaciones depende del nombre y contenido del evento que Pedidos publica. Si se modifica ese contrato, el consumidor debe revisarse.

No se afirma que Inventario dependa del evento: el escenario especifica que Inventario recibe la orden confirmada de Pedidos por otra relación.
